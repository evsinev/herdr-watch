# herdr-watch: Snapshot API

**Версия протокола:** 1
**Статус:** черновик
**Область:** только контракт HTTP-эндпоинтов. Способ получения данных с хостов (SSH, herdr socket API) вне области документа.

---

## 1. Назначение

Read-only endpoint, отдающий плоский снапшот состояния всех агентов одним GET-запросом, без SSE. Предназначен для клиентов, которым не нужен поток изменений и дорого держать долгоживущее соединение: встраиваемые устройства (ESP32 и аналоги), скрипты мониторинга, внешние интеграции.

Существующий SSE-эндпоинт остаётся без изменений. Snapshot API — дополнение, не замена.

---

## 2. Общие правила

| | |
|---|---|
| Базовый путь | `/api/v1/snapshot` |
| Метод | `GET` (других нет) |
| Content-Type ответа | `application/json; charset=utf-8` |
| Кодировка строк | UTF-8, без BOM |
| Именование полей | lowerCamelCase |
| Transfer-Encoding | только `identity`, `Content-Length` всегда явный |
| Аутентификация | наследуется от остального API |

Все ответы содержат стандартный заголовок `Date` (RFC 9110):

```
Date: Sat, 15 Aug 2026 11:32:07 GMT
```

Это единственный источник текущего момента времени сервера. В теле ответов `/agents` времени нет.

`Date` всегда в GMT и с точностью до секунды, часовой пояс сервера в нём не передаётся. Клиенту, которому нужно локальное время сервера или его смещение, следует использовать `/time` (§4).

`Date` присутствует и в ответах `304`, поэтому клиент может синхронизировать часы даже когда тело не менялось.

Оговорка для развёртывания за обратным прокси: если перед herdr-watch стоит nginx или аналог, `Date` формирует прокси, а не приложение. Расхождение часов между прокси и приложением клиенту не видно. Значения из `/time` берутся из процесса приложения и такому замещению не подвержены.

Порядок полей в JSON-объектах не гарантируется. Клиент обязан игнорировать неизвестные поля — это основной механизм расширения (см. §7).

## 3. `GET /api/v1/snapshot/agents`

### 3.1. Параметры запроса

| параметр | тип | по умолчанию | описание |
|---|---|---|---|
| `limit` | int, 1..200 | 200 | максимум записей в `agents` после сортировки |
| `view` | string | `full` | профиль ответа, см. §3.5 |

Значение `limit` вне диапазона → `400`. Отсутствие параметров — не ошибка.

`view` принимает значения из §3.5 без учёта регистра; неизвестное значение → `400`.

### 3.3. Поля верхнего уровня — `SnapshotResponse`

| поле | тип | nullable | описание |
|---|---|---|---|
| `protocolVersion` | int | нет | версия контракта, сейчас `1`. См. §7 |
| `sequence` | int64 | нет | монотонный счётчик состояния. Входит в `ETag` (§3.10). Не убывает в пределах жизни процесса, сбрасывается при рестарте |
| `agentCount` | int | нет | длина `agents` **после** применения `limit` |
| `agentTotal` | int | нет | общее число агентов **до** применения `limit`. Всегда `>= agentCount` |
| `agents` | array | нет | может быть пустым, `null` не допускается |

### 3.4. Элемент массива — `SnapshotAgent`

| поле | тип | nullable | лимит | описание |
|---|---|---|---|---|
| `host` | string | нет | 64 | идентификатор хоста из конфигурации herdr-watch |
| `project` | string | нет | 64 | basename корня git-репозитория. При невозможности определить — basename рабочего каталога |
| `branch` | string | нет | 128 | имя ветки. В detached HEAD — сокращённый SHA (7 символов) |
| `agentName` | string | нет | 32 | канонический идентификатор агента: `claude`, `codex`, `cursor`, `opencode` и т. д. Пустая строка — агент не распознан |
| `agentDisplay` | string | нет | 80 | отображаемое имя агента. См. §3.6 |
| `status` | string | нет | — | см. §3.6 |
| `statusCode` | int | нет | 0..4 | числовой эквивалент `status`, см. §3.6 |
| `hostStale` | boolean | нет | — | хост недоступен, запись отражает последнее известное состояние |
| `worktreePath` | string | нет | 256 | абсолютный путь чекаута на целевом хосте. Пустая строка — определить не удалось |
| `worktreeLabel` | string | нет | 64 | метка воркстри в herdr. Пустая строка — метки нет или это не воркстри |
| `linkedWorktree` | boolean | нет | — | `true` — linked worktree, `false` — основной чекаут репозитория |
| `detachedHead` | boolean | нет | — | HEAD отделён. При `true` поле `branch` содержит SHA (§3.4) |
| `prunable` | boolean | нет | — | git считает воркстри пригодным к `git worktree prune` (каталог удалён или недоступен) |

Строки обрезаются на сервере по границе кодовой точки UTF-8; обрезанное значение не помечается никак. Пустая строка допустима, `null` — нет.

`worktreePath` обрезается **с начала**, а не с конца: при превышении 256 символов сохраняется хвост пути, а в начало ставится `…`. Значимая часть пути — имя каталога, а не префикс.

Пара `host` + `worktreePath` уникальна в пределах одного ответа и стабильна между запросами, пока чекаут не перемещён. Это рекомендуемый ключ для сопоставления записей между опросами и для стабильной сортировки на клиенте. Пара `host` + `project` уникальной **не** является: на одном хосте может быть несколько воркстри одного репозитория.

Оговорка: при пустом `worktreePath` ключ вырождается. Такие записи клиенту следует считать неидентифицируемыми и не пытаться сопоставлять с предыдущим опросом. Полноценный `agentId`, не зависящий от файловой системы, запланирован на версию 2 (§7).

### 3.5. Профили ответа

Параметр `view` выбирает фиксированный набор полей записи `SnapshotAgent`. Профиль сокращает объём ответа для клиентов, которым не нужны все данные: встраиваемых устройств, простых индикаторов, скриптов.

| поле | `full` | `compact` | `status` |
|---|:---:|:---:|:---:|
| `host` | ✓ | ✓ | ✓ |
| `project` | ✓ | ✓ | ✓ |
| `branch` | ✓ | ✓ | — |
| `agentName` | ✓ | ✓ | — |
| `agentDisplay` | ✓ | — | — |
| `status` | ✓ | — | — |
| `statusCode` | ✓ | ✓ | ✓ |
| `hostStale` | ✓ | ✓ | ✓ |
| `worktreePath` | ✓ | — | — |
| `worktreeLabel` | ✓ | — | — |
| `linkedWorktree` | ✓ | — | — |
| `detachedHead` | ✓ | ✓ | — |
| `prunable` | ✓ | — | — |

Ориентировочный объём ответа при 20 агентах: `full` ≈ 3.2 КБ, `compact` ≈ 1.4 КБ, `status` ≈ 0.7 КБ.

Пример `GET /api/v1/snapshot/agents?view=compact&limit=2`:

```json
{
  "protocolVersion": 1,
  "sequence": 4417,
  "agentCount": 2,
  "agentTotal": 34,
  "agents": [
    {
      "host": "dqa1",
      "project": "paynet-ui",
      "branch": "feat/mfe-split",
      "agentName": "claude",
      "statusCode": 4,
      "hostStale": false,
      "detachedHead": false
    },
    {
      "host": "dqa2",
      "project": "paynet-forms",
      "branch": "main",
      "agentName": "codex",
      "statusCode": 2,
      "hostStale": false,
      "detachedHead": false
    }
  ]
}
```

**Внутри профиля состав полей фиксирован.** Все перечисленные поля присутствуют всегда; правило «`null` не допускается» (§3.4) действует без изменений. Профиль не опускает поля выборочно и не зависит от данных — клиент, зная имя профиля, знает точную форму записи и может парсить её без проверок на наличие ключей.

Поля верхнего уровня (§3.3) от профиля не зависят и присутствуют всегда.

Профиль влияет только на состав полей записи агента; поля верхнего уровня и заголовки от него не зависят. Сортировка (§3.9), применение `limit` и набор возвращаемых записей одинаковы во всех профилях: `status` не отбрасывает агентов, у которых нет git-данных, а `compact` не меняет порядок.

Назначение профилей:

- `full` — дашборд, отладка, интеграции, которым нужна полная картина, включая worktree-провенанс каждого агента;
- `compact` — встраиваемые клиенты с текстовым экраном. Содержит всё, что нужно для строки вида `dqa1 paynet-ui feat/mfe-split`, без presentation-полей и worktree-провенанса;
- `status` — индикаторы без текста: светодиодная панель, агрегат `max(statusCode)`, health-check.

Профиль `full` — значение по умолчанию и остаётся им во всех будущих ревизиях версии 1: клиент, не передающий `view`, никогда не потеряет поля.

Добавление нового профиля — совместимое изменение (§7). Изменение состава существующего профиля — несовместимое, поскольку клиент рассчитывает на фиксированную форму.

### 3.6. Идентификация агента

`agentName` — то, что определил детектор herdr. Значение стабильно, в нижнем регистре, без пробелов; пригодно для сравнения в коде и выбора иконки на клиенте. Набор значений открыт: herdr обновляет манифесты детекции независимо от herdr-watch, поэтому клиент обязан корректно вести себя при незнакомом значении, а не только при пустом.

`agentDisplay` — имя для показа человеку. Источники, в порядке приоритета:

1. presentation-переопределение, если хук или плагин прислал его в herdr (`display_agent`);
2. значение `agentName`, если переопределения нет.

Поле заполняется всегда, когда непусто `agentName`. Клиенту, которому нужна только строка для вывода, достаточно `agentDisplay`; `agentName` для этого использовать не следует, поскольку он игнорирует пользовательскую настройку.

Пустая строка в обоих полях означает, что в пане не распознан ни один агент. Такая запись всё равно попадает в выдачу, если herdr-watch считает пану активной; `status` в этом случае, как правило, `UNKNOWN` или `IDLE`.

`agentDisplay` может содержать любые печатные символы, включая пробелы, двоеточия и не-ASCII — оно задаётся пользователем. `agentName` ограничен `[a-z0-9._-]`. Клиентам с фиксированным шрифтом рекомендуется выводить `agentName`.

Ни одно из полей не участвует в сортировке (§3.9).

### 3.7. Статусы

| `status` | `statusCode` | смысл |
|---|---|---|
| `UNKNOWN` | 0 | агент не определён или состояние неизвестно |
| `IDLE` | 1 | простаивает, результат просмотрен |
| `WORKING` | 2 | работает |
| `DONE` | 3 | завершил, результат не просмотрен |
| `BLOCKED` | 4 | ждёт ответа человека |

`statusCode` упорядочен по возрастанию срочности: клиент может брать `max(statusCode)` как агрегат по всей панели без разбора строк.

Строковое и числовое представления дублируют друг друга намеренно: `statusCode` — для машинной логики, `status` — для читаемости в логах и при отладке `curl`.

В версии 1 набор статусов закрыт. При появлении новых значений в будущих версиях клиент обязан трактовать неизвестный `statusCode` как `0` / `UNKNOWN`, а не падать.

### 3.8. Git-счётчики коммитов (в v1 не отдаются)

Поля `aheadCommits`, `behindCommits` и `gitStale` в версии 1 **отсутствуют**. Причина: herdr 0.7.4 не предоставляет счётчиков ahead/behind ни в одной из выдач (`workspace list`, `agent list`, `worktree list`, `api snapshot`), а вычислять их git-плюмбингом в цикле опроса (отдельный медленный контур с `git fetch`) в v1 решено не реализовывать — это удорожает контур, крутящийся раз в 1–2 секунды по всем хостам.

Возможное добавление счётчиков — отдельным решением. Как новые поля это будет **совместимым** изменением (§7): они попадут в профиль `full` (и при необходимости в новый профиль), а состав замороженных профилей `compact`/`status` не изменится.

### 3.9. Сортировка

Сервер сортирует `agents`:

1. `statusCode` по убыванию;
2. `host` по возрастанию, лексикографически (byte order);
3. `project` по возрастанию, лексикографически.

Сортировка выполняется **до** применения `limit`. Клиент с ограниченным экраном, взяв первые N записей, получает самые срочные.

Порядок детерминирован при одинаковом `sequence`. При разных `sequence` порядок может измениться произвольно — привязываться к позиции элемента между запросами нельзя.

### 3.10. Кэширование

Ответ содержит `ETag`, идентифицирующий пару «состояние + представление»:

```
ETag: "compact-l20-4417"
Cache-Control: no-store
```

Формат: `"<view>-l<limit>-<sequence>"`. Значение непрозрачно для клиента — его следует хранить и возвращать целиком, не разбирая. Формат может измениться без смены версии протокола.

`ETag` обязан учитывать **все** параметры запроса, влияющие на тело ответа, а не только `sequence`: при неизменном состоянии разные `view` и `limit` дают разные тела. Иначе клиент, сменивший параметр, получил бы `304` и продолжил работать с предыдущим представлением.

При `If-None-Match`, совпадающем с текущим `ETag`, сервер отвечает `304 Not Modified` с заголовком `ETag` и без тела. Поддержка условных запросов обязательна для сервера; для клиента — рекомендуется.

Клиент, меняющий `view` или `limit` между запросами, не должен отправлять `If-None-Match` от предыдущего представления: ответ будет корректным (`200`), но условный запрос заведомо бесполезен.

Ответ `304` содержит заголовок `Date` (§2), поэтому клиент синхронизирует часы и при отсутствии тела. Дополнительных запросов ради времени не требуется.

## 4. `GET /api/v1/snapshot/time`

Параметров нет. Ответ `200 OK` — `SnapshotTime`:

```json
{
  "protocolVersion": 1,
  "serverTime": "2026-08-15T14:32:07+03:00",
  "serverEpoch": 1786012327,
  "timeZone": "Europe/Moscow",
  "utcOffset": 10800
}
```

| поле | тип | описание |
|---|---|---|
| `protocolVersion` | int | версия контракта |
| `serverTime` | string | ISO-8601 с офсетом, локальное время сервера |
| `serverEpoch` | int64 | Unix-время, секунды UTC |
| `timeZone` | string | IANA tz id сервера |
| `utcOffset` | int | смещение `timeZone` в секундах на момент `serverEpoch`, с учётом DST |

Условные запросы для этого эндпоинта не поддерживаются, `ETag` не выставляется. Заголовок `Date` присутствует, как и у остальных эндпоинтов.

Назначение — получить часовой пояс сервера и его смещение, чего стандартный заголовок `Date` не передаёт. Это единственный эндпоинт, отдающий время в теле.

Значения берутся из процесса приложения, а не из промежуточного прокси. `serverEpoch` и `Date` при корректно синхронизированных часах совпадают с точностью до секунды.

Рекомендуемая частота обращения — на старте клиента и далее не чаще раза в час: смещение меняется только при переходе на летнее время или смене конфигурации сервера. В остальное время достаточно `Date` из ответов `/agents`.

## 4a. `GET /api/v1/snapshot/usage`

Квота подписки Claude — утилизация 5-часового сессионного и недельного окон с временем их сброса. Совместимое дополнение (§7): отдельный эндпоинт, состав профилей `view` не изменён, `protocolVersion` остаётся `1`.

Параметров запроса нет. Ответ `200 OK` — `SnapshotUsage`:

```json
{
  "protocolVersion": 1,
  "state": "OK",
  "severityCode": 2,
  "capturedAt": 1787797108,
  "source": "ACCOUNT_API",
  "windows": [
    { "type": "five_hour", "usedPercent": 27, "resetsAt": 1787803200 },
    { "type": "seven_day", "usedPercent": 24, "resetsAt": 1788206400 }
  ],
  "models": [
    { "model": "Fable", "usedPercent": 14, "resetsAt": 1788206399 }
  ]
}
```

| поле | тип | описание |
|---|---|---|
| `protocolVersion` | int | версия контракта |
| `state` | string | `OK` \| `STALE` \| `NOT_CONFIGURED` |
| `severityCode` | int | `0` неизвестно/не настроено, `1` ok, `2` warning, `3` critical, `4` exhausted |
| `capturedAt` | int64 | Unix-время снятия показаний; `0`, если показаний не было |
| `source` | string | кто наблюдал показания: `NONE` \| `STATUSLINE` \| `ACCOUNT_API`; набор значений открыт |
| `windows` | array | по записи на каждое **отчитавшееся** окно; может быть пустым, `null` не бывает |
| `models` | array | недельные окна, привязанные к моделям; пустой массив, если их не отдали |

Элемент `windows` — `SnapshotUsageWindow`:

| поле | тип | описание |
|---|---|---|
| `type` | string | `five_hour` \| `seven_day`; набор значений открыт |
| `usedPercent` | int | утилизация, целые проценты `0..100` |
| `resetsAt` | int64 | Unix-время сброса окна |

Элемент `models` — `SnapshotUsageModelWindow`:

| поле | тип | описание |
|---|---|---|
| `model` | string | имя модели, **как его прислал сервер**; набор моделей открыт |
| `usedPercent` | int | утилизация, целые проценты `0..100` |
| `resetsAt` | int64 | Unix-время сброса окна |

**Отсутствие = пропуск.** Окно, о котором показаний нет, в массив не попадает вовсе — ни с нулём, ни с `null` (§3.4). Пустой `windows` — валидное состояние, а не ошибка.

**`severityCode`** — та же идиома «один int вместо разбора» что и `statusCode` (§3.5): равен худшей полосе среди отчитавшихся окон. Полосы: `1` до 70 %, `2` от 70 %, `3` от 90 %, `4` при 100 %. `0` означает, что полосу взять неоткуда — показаний нет ни по одному окну. `STALE` сам по себе полосу не занижает: о свежести говорят `state` и `capturedAt`.

**`source` — не украшение.** У одних и тех же цифр с одним и тем же возрастом разный смысл в зависимости от того, кто их наблюдал. `STATUSLINE` — показания, которые приносит statusline-хук Claude Code: они двигаются, только пока на машине herdr-watch запущена сессия. `ACCOUNT_API` — опрос аккаунт-эндпоинта: видит и расход с других машин, но ходит по интервалу и может замолчать при недоступности сети или rate-limit. `NONE` — показаний не было ни от кого. Значение никогда не `null` и никогда не пустое. Набор значений открыт: незнакомое имя источника клиент обязан показать как есть, а не считать ошибкой.

**`models` — только от `ACCOUNT_API`.** Помодельные недельные окна отдаёт лишь аккаунт-эндпоинт. При этом массив **не привязан к `source`**: показания 5h/7d выбираются по свежести, а statusline обновляется чаще пятиминутного опроса и обычно выигрывает — если бы разбивка ехала вместе с победителем, она мигала бы, появляясь на секунды раз в пять минут. Поэтому `models` берётся из последнего ПРИГОДНОГО показания аккаунт-эндпоинта и может стоять рядом с `source: STATUSLINE`; окна, `source` и `capturedAt` при этом принадлежат победителю, как и раньше. Когда аккаунт-эндпоинт деградировал (его показание помечено устаревшим), массив пустеет вместе с ним — застывшая навсегда разбивка была бы хуже её отсутствия. Пустой массив — честное «таких данных нет», а не пробел. Набор моделей **открыт** (`Fable`, `Opus`, `Sonnet`, `Design`, …): модель, о которой клиент не слышал, приходит как есть и должна отображаться как есть. Окна, о котором показаний нет, в массиве не будет вовсе — нулём отсутствие не кодируется. `models` **не влияет** на `severityCode`: тот по-прежнему считается только по 5-часовому и недельному окнам, чтобы значение не поменяло смысл для уже работающих устройств.

**Свежесть.** Цифры двигаются только пока запущена сессия Claude Code, поэтому запись может быть сколь угодно старой. `state = STALE` означает, что запись старше порога сервера (или файл стал нечитаем) — данные всё равно отдаются, с прежним `capturedAt`. Клиенту следует показывать возраст, а не выдавать старые цифры за текущие.

**Кэширование.** `ETag` формата `"usage-<capturedAt>"`, `Cache-Control: no-store`, `If-None-Match` → `304` без тела, с `ETag` и `Date` (§3.10). Валидатор непрозрачен, формат может измениться без смены версии протокола. Опрос чаще, чем идут показания, — обычный режим для этого эндпоинта, и почти всегда даёт `304`.

Рекомендуемая частота опроса — 30–60 с: чаще смысла нет, показания появляются не чаще смены состояния сессии Claude Code.

Источник данных — не сеть и не учётные данные: показания приносит statusline-хук Claude Code на самой машине herdr-watch, поэтому квота относится к **аккаунту** Claude, а не к какому-либо хосту из `/agents`.

## 5. Коды ответов и ошибки

| код | когда |
|---|---|
| `200` | успех |
| `304` | `If-None-Match` совпал с текущим `ETag` |
| `400` | `limit` вне диапазона или не число; неизвестное значение `view` |
| `503` | сервис не завершил первичную инициализацию |

Тело ошибки:

```json
{
  "error": "invalid_parameter",
  "message": "limit must be between 1 and 200"
}
```

`error` — стабильный машиночитаемый код, `message` — человекочитаемое пояснение, может меняться без смены версии протокола.

Коды `error`: `invalid_parameter`, `not_ready`, `internal_error`.

Недоступность отдельных хостов ошибкой не является: такие агенты возвращаются в `200` с `hostStale = true`. Ответ `200` с пустым `agents` — валидное состояние, означающее, что живых агентов нет.

## 6. Требования к клиенту

Обязательные:

- игнорировать неизвестные поля в объектах;
- трактовать неизвестный `statusCode` как `0`;
- не отказывать при незнакомом `agentName` — набор значений открыт и пополняется на стороне herdr; неизвестный агент выводится как есть, с нейтральной иконкой;
- не полагаться на порядок ключей в JSON;
- проверять `agentTotal > agentCount` перед выводами о полноте списка: при усечении часть агентов в ответ не попала.

Рекомендуемые:

- отправлять `If-None-Match` и обрабатывать `304`, храня `ETag` как непрозрачную строку;
- брать текущее время из заголовка `Date`, а не запрашивать `/time` в каждом цикле;
- запрашивать минимально достаточный профиль `view` (§3.5), а не `full` по умолчанию;
- при `protocolVersion` больше известного клиенту — работать по известным полям, а не отказывать;
- интервал опроса не чаще 1 с; для встраиваемых клиентов — 5–15 с;
- при `503` — повтор с экспоненциальной задержкой, начиная с 1 с.

## 7. Версионирование

`protocolVersion` меняется только при несовместимом изменении. Совместимыми и **не** повышающими версию считаются:

- добавление новых полей в любой объект;
- добавление нового значения `view`;
- добавление новых query-параметров с безопасным значением по умолчанию;
- изменение формата значения `ETag`;
- добавление новых значений `error`;
- изменение текста в `message`.

Несовместимыми считаются: удаление или переименование поля, изменение типа, изменение семантики существующего поля, добавление нового значения `statusCode`, **изменение состава существующего профиля `view`** — клиент рассчитывает на фиксированную форму ответа для выбранного профиля.

Новое поле, добавленное в версии 1, попадает в профиль `full` и, при необходимости, в новый профиль. В `compact` и `status` состав заморожен. Клиенту, которому нужен состав, отличный от трёх существующих, следует запросить добавление нового профиля, а не изменение имеющегося.

Добавление эндпоинта `/api/v1/snapshot/usage` (§4a) сделано по этим правилам: новый путь, существующие ответы не тронуты, версия не повышена.

Поля `source` и `models` в ответе `/api/v1/snapshot/usage` (§4a) добавлены по тем же правилам: новые поля в существующем объекте, состав профилей `view` эндпоинта `/agents` не тронут, `severityCode` считается по-прежнему, версия остаётся `1`. Клиент версии 1, написанный до их появления, продолжает работать, просто их игнорируя.

При выпуске версии 2 путь меняется на `/api/v2/snapshot/...`. Версия 1 остаётся доступной минимум один минорный релиз herdr-watch после выпуска версии 2.

Запланировано на версию 2 (не реализовывать в клиентах версии 1): стабильный `agentId`, не зависящий от путей файловой системы, поля `workspaceId` и `paneId`, признак наличия незакоммиченных изменений в чекауте.

## 8. Что реализуется на стороне herdr-watch

Вне контракта, для планирования работ:

- источник `branch` — поле `branch` записи `herdr worktree list`, уже собираемой в кадре `SshSource`; в detached HEAD (`is_detached`) подставляется короткий SHA (первые 7 символов);
- `aheadCommits`/`behindCommits`/`gitStale` в v1 **не отдаются**: подтверждено на реальном выводе herdr 0.7.4, что счётчиков ahead/behind нет ни в `workspace list`, ни в `agent list`, ни в `worktree list`, ни в `api snapshot`; git-плюмбинг в цикл опроса не добавляется (§3.8);
- `sequence` — монотонный счётчик обновлений состояния в `Registry`, общий с SSE; инкрементится на каждую мутацию;
- источник worktree-провенанса — `herdr worktree list --workspace <id>`, уже собираемый в кадре `SshSource` и хранимый в `Registry` (вложенным в `WorkspaceInfo.worktrees`). Флаги `is_detached`/`is_prunable`/`is_linked_worktree` берутся оттуда напрямую. Snapshot API отдаёт только провенанс агентов; полный список чекаутов остаётся доступен через SSE API и в версии 1 наружу не выводится;
- провенанс на записи агента (`worktreePath`, `worktreeLabel`, `linkedWorktree`) резолвится через воркспейс агента (`workspace_id` агента → worktree с тем же `open_workspace_id`); при отсутствии привязки поля заполняются пустыми значениями и `false`, а не опускаются;
- `agentName` берётся из поля `agent` записи `herdr agent list`; `agentDisplay` — из `display_agent`, если оно есть, иначе копия `agentName`. В herdr 0.7.4 `display_agent` отсутствует, поэтому в v1 `agentDisplay` всегда равен `agentName`;
- профили `view` реализуются отдельными record-типами (`SnapshotAgent`, `SnapshotAgentCompact`, `SnapshotAgentStatus`) с проекцией из полного объекта, а не динамической фильтрацией полей. Это даёт различимые схемы в OpenAPI и типизированные классы у клиентов, генерирующих код из спецификации;
- профиль `status` не требует резолвинга worktree-провенанса — при его запросе эти данные можно не читать из `Registry`;
- каждый профиль покрывается golden-файлом в тестах: фиксированный состав полей делает такой тест исчерпывающим;
- источник квоты (§4a) — файл `~/.config/herdr-watch/claude-usage.json`, который пишет статус-строка Claude Code (`statusline-rust/`, бинарник `herdr-watch-statusline`); herdr-watch читает его по mtime и держит последний снапшот в `Registry` рядом с картой хостов. Наружу тот же снапшот уходит и в SSE-событии `claude_usage`, и в `GET /api/claude-usage` — Snapshot-представление отличается только запретом `null` (§3.4);
- второй, необязательный источник квоты — опрос аккаунт-эндпоинта Anthropic (`herdr-watch.claude-usage.source: pull | auto`, по умолчанию `push` = только statusline). Он требует уже имеющегося креденшла Claude Code (только чтение) и отдельного осознанного согласия на отправку клиентского отпечатка, поэтому по умолчанию выключен и никаких исходящих запросов не делает. `Registry` держит последнее показание **каждого** источника и публикует наблюдённое позже; `source` в ответе показывает, чьё именно показание отдано.
